# 语料层 → 判定层：晋升管道与边界

日期：2026-10-31 · 引擎 `chemcritic-engine/1.5.0` · 契约回归 9/9 · 自检 28/28

## 1. 为什么做这件事

10/31 上午的语料库扩充（114 篇 / 194 表 / 1981 行）解决的是「库里有多少东西」。
但语料躺在 `data/corpus/` 里，SciencePal 沙箱没有那个目录，`records.json` 也没变——
**agent 查不到、判定用不上**，它只是一堆仓库里的文件。

用户的原话：

> 「不要只把 PDF 加到文档里就不管了。还要核验加到 records.json 还有 engine 的 py 里，
>   agent 才可以调用。」

所以这一轮做的是**通道**，不是再做一批采集。

## 2. 三层证据结构（本次定稿）

| 层 | 位置 | 规模 | 参与判定 | 谁可以看 |
|---|---|---|---|---|
| 采集面 | `data/corpus/2026-10-31.json` + `docs/corpus/cards/` | 114 篇 / 194 表 / 1981 行 | ❌ | 人（读全文） |
| 检索面 | `data/corpus_index.json` → 内嵌进引擎 `--corpus-query` | 194 表（表级） | ❌ `judgeable=false` | agent（沙箱内） |
| 判定面 | `data/records.json` | **175 条 entry** | ✅ | agent（`--list-records` / 判定） |

检索面存在的唯一理由：让 agent 能回答「库里有没有关于这个底物的文献数据、报了多少、区间多少」，
同时**不能**拿那些数字去算差值。每个返回体都带 `"judgeable": false` 和一句边界声明。

## 3. 三步管道（可复现，不是手工搬运）

```
scripts/triage_corpus.py          194 表 → A_ready 13 / B_partial 119 / C_reject 62
        ↓
scripts/promote_corpus.py         规则抽取 → data/incoming/corpus_promote_2026-10-31.json
        ↓  （26 张表 / 246 entry）
scripts/merge_corpus_records.py   逐条过 gates.label_supported → records.json
        ↓
data/records.json                 44 → 175 条
```

关键设计：**merge 的门槛就是判定的门槛**。它 `import gates.label_supported`，
用与引擎完全相同的函数检查 label_raw 是否支撑口径——入库标准和判定标准不允许是两套。

### 3.1 分诊（triage）规则

- `A_ready`：表头有 yield 列 + 题注/脚注含 reaction conditions 与投料量 + 题注内底物骨架词 ≥2 类
- `B_partial`：有收率列但条件或底物要到正文补
- `C_reject`：不是「一个反应实例的收率」——活性/TOF/ee/晶体学键长/二次文献转引

`C_reject` 62 张里，有 21 张是**二次文献的对比表**（caption 明写 "Comparison of ... by Trudell/Nolan"，
脚注无 reaction conditions，数值转引他人）。这类表最容易被误当成「文献数据」，
实际连底物都不在本表里，判 reject 是对的。

### 3.2 晋升（promote）只做「双底物交叉偶联」

只处理 Suzuki / Buchwald–Hartwig / Sonogashira / Heck / Negishi——只有这类能填满
gate 1 要求的底物组合。其余 13 类反应（photoredox、borylation、metathesis…）留在检索面。

抽取的三条铁律：
1. **抽不出写 null**，绝不用默认值补成事实
2. **evidence_grade 最高 candidate**——语料层只有 efetch 表格文本，没有 PDF 图证，
   给 A_confirmed 就是造假
3. **label_raw 必须是表头/题注逐字片段**，不改写（gate 4 用它判口径一致性）

抽取过程中修掉的 5 个真错（都来自「正则跨句吞半句话」）：
- `_label_map` 把 `(Section 2)). When the reaction of ...` 当成化合物名 → 名字模式收紧为单词序列，遇叙述词即停
- `4-bromotoluene (1 equiv.` 未闭合括号残渣 → 名字清洗，清不干净返回 None
- 脚注只列裸名（`styrene, 4-iodotoluene, base (2 mmol)`）时抽不到 → 增加裸名单兜底
- `Ar-X` / `aryl halide` 通称被当底物 → 标 `generic_substrate`，整表拒绝入库
- `Pd-Ag` 类格氏试剂无 partner 类别 → 新增 `organometallic`

| 改动 | 文件 | 为什么必须改 |

### 数字从 175 降到 140 的原因

第一版有 35 条是**构造错**的，验收时被平台侧复现出来（详见第 8 节）：

- 12 条来自一张**底物范围表**（表头 `Olefin | X | R1`），12 行分别是苯乙烯 / 丙烯酸甲酯 /
  甲基丙烯酸甲酯 / 丙烯腈和 I / Br / Cl，脚注却是一句模板「iodobenzene, methyl acrylate」。
  按脚注给整表打同一个底物对，等于把 11 个不同反应说成同一个。
- 1 条是**阴性对照**（Pd 0.0 mol%，收率 0），留在池里把区间下界拉到 0。
- 22 条来自同类范围表与空白行。

140 是真数。**库的规模是采集问题，判定层的规模是纪律问题**——这一轮把纪律补上了。

## 7. 答辩口径

三句话：

1. **数量**：语料 114 篇 194 表 1981 行，其中 96 条真的进了判定层，剩下的是检索面。
2. **纪律**：晋升的天花板是 `candidate`，因为只有表格文本没有 PDF 图证；
   入库门槛直接复用 `gates.label_supported`，入库标准和判定标准是同一个函数。
3. **边界**：7 张范围表 + 8 张底物通称表拒绝入库，因为底物随行走——需要行级结构解析，本轮不做，写明不做。

反例准备（评委可能问「那你为什么不多塞点」）：
塞进去的结果是 `imported_unchecked` 或底物对不上，判定时一律 UNKNOWN/FAIL——
库里数字变多，能比的对数不变，只多了 130 条噪音。所以不塞。

## 8. 平台验收反馈 → 修正（同日，引擎 1.5.0 → 1.6.0）

平台侧新开会话实测后，报告里出现三处自相矛盾，逐条追下来是五个真 bug，
**都不是显示问题，是数据构造错**。

### 8.1 报告里的三处矛盾

| 报告里写的 | 实际是什么 | 根因 |
|---|---|---|
| 「56 条以 iodobenzene 为芳基卤」 | 真实 31 条 | 12 条来自底物范围表；13 条把 `1-chloro-4-iodobenzene` 用子串匹配算进 iodobenzene |
| 「表 1 值 0–96%」 | 真实 60–96% | 第 14 行是 Pd 0.0 mol% 的**空白对照**，收率 0 |
| 「status = PLACED」+「产物结构未确认」 | 两句互相打脸 | 上一版把「产物未记录」当作放行，放行被写成 PLACED |

### 8.2 五个 bug 与修法

**(1) 底物范围表被当成单底物对**（最严重，虚增 12 条假参照）

表头出现 `Olefin / X / R1 / Product / Substrate` 这类列，且该列在行内取 ≥2 个不同值时，
说明**底物随行走**；脚注里那句「Reaction conditions: iodobenzene, methyl acrylate」
只是 model reaction 的模板条件，不是整表的底物。

→ `promote_corpus.py::_scope_columns()` 检出 → `merge_corpus_records.py` 拒绝入库。
命中 7 张表。这类表需要行级结构解析，本轮不做，写明不做。

**(2) 阴性对照进了参照池**

收率为 0 且催化剂用量为 0 或 `-` 的行是空白/阴性对照，不是催化结果。
留在池里会让区间下界变 0，「0–96%」看着像文献分散度，其实是「不加催化剂的必然结果」。

→ `_blank_control_rows()`，两种写法都认（`0.0` 与 `-`/`none`+收率 0）。剔 3 行。

**(3) 亲核试剂抽成了添加剂**（化学错误）

PMC9301730 标题是 Buchwald–Hartwig 胺化（C–N 成键），苯硼酸酯只是**活化剂**，
真正的亲核试剂是甲苯胺。按「硼酸 → Suzuki」的优先级抽，会得出「芳卤 + 硼酸酯」这种
不存在的 Suzuki 底物对——平台盘点里第 4 条就是它。

→ 候选改为**全量收集**，反应类型只在多候选时打破平局。
同时反向也修：PMC8402173 一篇里 Heck 与 Sonogashira 并存，表级关键词写成 `heck`，
但表里是 4-碘苯甲醚 + 苯乙炔 → 按炔改回 Sonogashira（记 `class_corrected`）。

**判据顺序：底物证据 > 标题关键词。** 标题是关键词粗归类，底物名是原文写的。

**(4) 产物"不知道"被写成"通过"**

这是上一版自己埋的：为了不让产物只有编号的记录全被排除，改成「一侧为空不阻断」。
结果 `status = PLACED`，而报告正文又说「产物结构未确认」。

→ 产物关系改为四态，且**只有"两侧都记录了且判同"才算 PLACED**：

| 状态 | 含义 | 能否给差值 |
|---|---|---|
| `same` | 两侧都记录产物名且判同 | 能，`delta_basis = product_recorded` |
| `inferred` | 两侧都未记录，但底物键名推出的反应类型一致 | 能，但**必须**带推定声明 |
| `unconfirmed` | 推不出反应类型 | 不能，只并排 |
| `diff` | 两侧都记录且确实不同 | 排除出参照池 |

对应三个新 status：`PLACED` / `PLACED_PRODUCT_INFERRED` / `PLACED_PRODUCT_UNCONFIRMED`。

**(5) 条数被当成独立证据数**

一篇文献一张条件优化表报 13 个点，按「13 条参照」呈现是虚增证据量。
提示词里早就写了 `non_independent`，但引擎从未实现。

→ `source_count` / `non_independent` 落地。上述实测：`reference_count = 12`，
`source_count = 1`，`non_independent = true` → 报告必须说明「这 12 条同属一篇文献」。

### 8.3 顺带修掉的两个陈旧 bug

- `catalyst_form = "none"` **不在受控词表**里，写了等于永远算不出档位。
  且「没抽到催化剂」与「原文明确无催化剂」是两件事，前者不该被表述成任一形态。
- `Pd/mol %` 被当作催化剂名写进记录（用量列 ≠ 化合物）。

同时补了两件事，让档位可算率从 24/96 提到 36/96：
- 行级条件覆盖（溶剂/碱/温度/时间以行为准，脚注只给表级兜底）；
- 催化剂形态从题注/首段捞（`_form_from_text`，只认含 Pd/Ni/catalyst 的那一句，
  避免把「与 Pd/C 相比」这类对比句当成本文催化剂）。

### 8.4 修正后实测

```
iodobenzene + methyl acrylate, isolated 70%
  status        PLACED_PRODUCT_INFERRED
  tier          C（同档）
  reference     12 条，区间 60–96%，source_count = 1，non_independent = true
  delta         vs_min +10，vs_max −26，basis = reaction_class_inferred
  caveat        产物结构系由底物类别推定，不是原文逐字给出
```

验证：契约 **9/9**、自检 **28/28**、`build_bundle --check` 一致。

### 8.5 剩下的边界（评委可能问）

- 仍无 PDF 图证 → 天花板 `candidate`。
- 60 条档位算不出（催化剂只在正文、溶剂缺失）。全部带 `tier_problem` 说明原因，
  绝不回退成「跨档全池」。这是设计：**算不出档位就给 delta 是假精确**。
- 7 张范围表不做行级解析，理由与影响都写在 8.2(1)。

一句话：**这一轮把「数字好看」换成了「每条都站得住」。**
