## 一、产品定位

### 1.1 清晰定位

ChemCritic 是一款**实验结果复盘与下一步排查辅助 Agent**，首期聚焦有机合成中的单次反应结果。它从“我已经做完这次实验，结果如何解释？”开始，而不是从目标分子开始预测合成路线，也不控制实验设备或代替实验者决策。

**目标用户：** 有机合成方向的本科生、研究生及科研人员，尤其是需要复盘低收率、产物不明确或实验重复性不稳定的用户。

**核心任务：**

- 把用户的实验记录整理为可比较的结构化记录；
- 通过 SciencePal 检索并展示相关文献/先例；
- 将实验观察、用户目标和可比先例分开对照；
- 提示可能值得优先调查的因素及其证据、反证和不确定性；
- 记录用户后续实验结果，方便回顾每轮决策。

**产品承诺：** 帮研究者更快、更有条理地复盘实验，并让依据可检查。系统输出的是研究辅助信息和待验证方向，不保证自动找出真实失败原因，也不宣称建议一定提升收率。

### 1.2 不做什么（MVP 边界）

- 不自动控制实验设备或执行化学实验；
- 不把单篇文献中的典型收率当作普适成功阈值；
- 不仅凭低收率断定某个变量就是失败原因；
- 不生成没有可核验来源的文献引用；
- 不在首版同时覆盖所有反应类别。先选一个团队能审查、能找到可靠先例的反应类别做深。

## 二、用户痛点与价值

实验结果出来后，研究者通常要在实验记录、表征结果与文献之间来回查找；当结果不理想时，可能的原因涉及反应本身、试剂状态、反应条件、后处理和纯化。把单一变量直接归因为“失败原因”往往没有充分证据。

ChemCritic 的价值假设是：将这些材料放进同一个复盘流程，减少重复整理和检索，并更清楚地呈现“观察到了什么、文献支持什么、还不能确定什么、下一步怎样区分不同假设”。

**价值验证指标（黑客松可测）：**

1. 一个测试案例从输入到带来源的复盘结果能否稳定跑通；
2. 检索来源是否可打开，引用内容是否支持对应陈述；
3. 对缺字段、无匹配先例、互相矛盾证据，Agent 是否能追问或明确保留结论；
4. 邀请 3–5 位目标用户试用，记录完成一次复盘所需时间、输出可理解性及建议可执行性反馈。

## 三、产品流程与输出

### 3.1 Agent 工作流：Observe → Retrieve → Assess → Investigate → Learn

1. **Observe（采集）**：用户填写或上传反应物/产物、反应类型、条件、收率、纯度和表征结果；关键字段缺失时 Agent 先追问。
2. **Retrieve（检索）**：调用 SciencePal 搜索与反应物、反应类型、条件或产物相关的资料，展示来源元数据、原文片段/摘要和链接。将“检索到的文献”与“团队准备的演示数据”明确区分。
3. **Assess（评估）**：用确定性规则检查目标产物证据、用户设定目标及已检索到的可比数据，返回结果状态与触发规则。
4. **Investigate（排查）**：基于已核验先例提出有限数量的候选调查方向。每条包含证据、与当前实验的差异、可能反证、置信/证据等级和可区分假设的下一步实验建议。
5. **Learn（记录）**：用户确认或补充后，将本轮实验与后续结果按项目保存，形成可回看的实验迭代记录。MVP 只做记录和检索，不声称仅凭少量案例就会自动学习出可靠模型。

### 3.2 输出格式

每次复盘应至少包含：

- **结果状态**：目标产物已确认 / 部分达到目标 / 未确认或证据不足；
- **判定依据**：引用了哪些用户输入、规则、用户目标或可比文献数据；
- **检索证据**：每个来源的标题、作者/年份（可获取时）、链接、相关内容及其与当前实验的可比程度；
- **候选调查方向**：按优先级列出，不超过 3 条；
- **证据与不确定性**：支持点、反证/差异、尚缺信息；
- **建议的验证步骤**：提出能区分不同假设的下一步实验设计方向，由用户审阅决定是否执行；
- **局限提示**：文献条件、底物、分析方法和本次实验可能不可直接比较。

### 3.3 SciencePal 的核心使用

SciencePal 必须进入“检索证据 → 影响复盘输出”的主链路。演示时要展示实际检索词、命中的来源，以及这些来源如何支持、限制或改变某条候选方向。若当前平台能力只能通过人工复制检索结果，应在项目说明中如实披露工作流和人工步骤，不得伪称 API 集成或自动化能力。

## 四、MVP 范围与验收标准

### MVP 必做

- 一个经过团队选择的反应类别；
- 一个结构化实验输入表单和字段校验；
- SciencePal 文献检索及来源展示；
- 可解释的规则判定；
- 证据、推断、不确定性分开展示；
- 至少 3 个演示/验证案例（包含证据不足或信息缺失的案例）；
- 每条建议能够追溯到真实来源；
- 简单的历史记录功能；
- 可访问的演示入口和备用录屏/静态结果。

### 暂缓功能

- 全反应类型覆盖、自动批量导入各类实验记录；
- 大规模反应数据库清洗和复杂向量检索；
- 贝叶斯优化、收率预测模型、多目标条件优化；
- 自动谱图解析、自动实验控制或多智能体协作。

### 完成定义

评审可从一个可访问入口完成“输入案例 → SciencePal 检索 → 查看来源 → 查看判定及理由 → 查看候选排查方向与局限 → 保存/查看记录”的主流程；演示中的文献和案例均可核验，且团队能说明验证方法、资源来源和当前限制。

## 五、竞争格局与竞争力

### 5.1 市场判断

相关产品和研究并不少，化学 AI 已覆盖反应条件推荐、收率预测、实验优化、高通量分析、实验室自动化和文献辅助。直接或邻近产品包括：

| 类别/产品 | 主要方向 | 与 ChemCritic 的关系 |
|---|---|---|
| Elementics AI REACTOR | 配方故障排查，利用文献、专利等来源给出调查方向 | 最接近“基于证据排查失败”的商业案例，但侧重配方/材料场景 |
| AutoRxn | 基于实验结果进行贝叶斯反应优化并建议下一批条件 | 邻近竞品，重心是优化实验设计和实验循环 |
| Mestrelab Chrom Reaction Optimization | 高通量反应数据处理、比较和归档 | 邻近工具，重心是分析流程和条件比较 |
| ChemEtrian、ScaleChem 等 | 综合化学研发、反应优化、预测或工艺分析 | 平台级替代方案，功能较广，面向专业研发团队 |
| ASKCOS、Chemist-X 等研究/工具 | 合成规划或反应条件推荐 | 更偏预测/推荐，不等同于从单次实测结果出发的复盘 |

因此不能宣称“市场上没有相关产品”。更稳健的结论是：**赛道竞争活跃，相关能力分散；ChemCritic 的差异化假设在于轻量地从单次实测结果进入，把判定依据、文献先例、未证实假设和下一步验证整合在一个可追溯的复盘流程中。** 该差异仍需通过产品试用和竞品调研验证。

### 5.2 竞争力假设

1. **入口差异：** 从“我这次实验发生了什么”开始，而非只做目标反应条件预测。
2. **低门槛：** 不依赖机器人或高通量平台，面向手工实验和教学/小团队复盘。
3. **可信度设计：** 规则判定和模型推断分离；引用逐条可核验；证据不足就保留结论。
4. **可复盘闭环：** 将本轮结果、依据和后续实验连起来，方便用户和团队回看。
5. **SciencePal 原生工作流：** 让科学文献检索真正参与核心研究任务，而非只用作外围问答或文案生成。

### 5.3 竞争力成立的条件

- 找到与用户反应在底物、反应类型、条件和分析方法上足够可比的先例；
- 输出的建议不是“升温/换溶剂/加催化剂”式通用清单，而能说明为什么值得调查以及如何验证；
- 有目标用户反馈和小规模案例核验支撑“省时、易用、可信”的价值主张；
- 对数据来源、适用范围和不能推断的事项保持透明。

## 六、创新点与边界

### 6.1 可 defensible 的创新表述

1. **以实测结果为中心的科研 Agent 工作流**：把单次实验记录作为任务上下文，组织检索、判定、排查和迭代记录。
2. **判定与诊断分层**：规则引擎只做输入和目标的可解释对照；LLM 不负责宣判实验成败。
3. **证据链和不确定性作为一等输出**：每项调查方向关联来源、可比性、反证和缺失信息。
4. **从猜原因转向设计区分性验证**：给出能区分候选解释的下一步实验思路，而非声称找到了唯一真因。
5. **面向普通手工实验的轻量使用路径**：不以硬件自动化为前提，先帮助用户整理已有数据和文献。

### 6.2 不应夸大的点

“LLM 化学建议”“反应优化”“文献 RAG”本身都不是新概念。ChemCritic 的创新应强调工作流组合、单次实验入口、证据可追溯和不确定性处理；不能仅凭概念或演示案例宣称技术突破、诊断准确率高或市场空白。

## 七、技术方案与技术栈

### 7.1 推荐 MVP 架构

```text
Streamlit 输入/结果页
        │
        ├── Pydantic 输入校验与规范化
        ├── SciencePal 检索（按平台实际能力接入；保留来源与检索记录）
        ├── Python 规则引擎（判定状态和理由）
        ├── LLM 编排/结构化输出（只做证据归纳、候选假设与追问）
        └── SQLite 案例记录与复盘历史
```

### 7.2 技术选型

| 层 | MVP 选型 | 选择理由/约束 |
|---|---|---|
| 界面 | **Streamlit** | 快速实现表单、案例结果和来源展示；只选一种前端框架，减少集成成本 |
| 运行时 | **Python 3.11+** | 规则、数据校验和原型开发生态成熟 |
| 数据模型 | **Pydantic + JSON Schema** | 校验必填字段、单位和数据类型，拒绝不完整输入或提示补充 |
| SciencePal 使用 | **优先使用平台内可用的检索/Agent 能力**；若无可调用接口，采用透明的人工检索工作流并记录来源 | 赛题要求核心环节实质性使用 SciencePal；不得假设存在未确认的 API |
| 文献检索与证据存储 | MVP 先用 SciencePal 检索结果 + 经人工核验的 JSON/CSV 案例集 | 小规模先例库先做可追溯，不先搭复杂向量库；将标题、作者、年份、DOI/URL、条件、结果及摘录分字段存储 |
| Agent/LLM | 平台支持的模型/Agent 能力；必要时使用团队已获准的模型 API，要求 JSON 结构化输出 | LLM 负责归纳、追问和候选解释，不得改写引用事实或取代规则判定；记录模型和提示版本 |
| 规则引擎 | 纯 Python 函数 | 同一输入得到稳定结果；规则及触发理由可展示和单元验证 |
| 持久化 | **SQLite** | 原型阶段无需独立数据库服务，保存项目、实验输入、来源和复盘输出 |
| 部署 | SciencePal 可分享的 Agent/工作流作为首选；外部演示页仅在必要时使用 Streamlit Community Cloud 或团队可访问环境 | 评审链接须在截止前确认权限、稳定性和访问方式；以真实可部署条件为准 |
| 版本与材料 | Git（代码/配置）、README、案例来源清单、资源声明 | 便于复现，并区分赛前已有与赛期新增内容 |

### 7.3 检索策略

- **MVP 不以向量库为前提。** 小型、人工核验的案例集先用结构化字段过滤 + 关键词检索，方便检查错误来源。
- 若案例积累后需要语义召回，再增加 Chroma 或 FAISS；向量检索只负责候选召回，最终引用必须回到原始记录/来源核验。
- 优先记录 DOI、出版社页面或数据库永久链接。搜索摘要不能代替原始来源核验。
- 每条证据注明匹配维度和限制，例如反应类型相同但底物不同、分析方法不一致。

### 7.4 LLM 输出约束

- 使用固定 JSON 输出字段：状态、观察事实、来源证据、候选假设、支持点、反证、缺失字段、建议验证步骤、局限。
- 无来源的主张不得标注为文献结论；检索未命中时返回“当前证据不足”。
- 将用户提供的数据和检索证据作为不可信输入处理，防止模型把提示内容当成系统规则。
- 保存检索来源及模型版本，演示输出可复现。

## 八、数据结构与判定规则

### 8.1 示例输入

```json
{
  "experiment_id": "demo-001",
  "reaction": {
    "name": "Suzuki coupling",
    "reactants_smiles": ["...", "..."],
    "target_product_smiles": "..."
  },
  "conditions": {
    "solvent": "THF",
    "catalyst": "Pd(PPh3)4",
    "temperature_C": 60,
    "time_h": 12,
    "equivalents": {"aryl_halide": 1.0, "boronic_acid": 1.2},
    "atmosphere": null,
    "scale_mmol": null
  },
  "results": {
    "yield_pct": 35,
    "purity_pct": 90,
    "product_confirmed": true,
    "characterization": ["NMR"],
    "notes": "NMR 与目标产物一致"
  },
  "user_goal": {
    "minimum_yield_pct": null,
    "minimum_purity_pct": null
  }
}
```

### 8.2 状态判定

| 状态 | 触发逻辑 |
|---|---|
| **目标产物已确认** | 用户提供的表征支持目标产物；是否满足目标指标另行展示 |
| **部分达到目标** | 产物得到支持，但未达到用户自定义的收率/纯度/选择性目标，或低于足够可比的先例范围 |
| **未确认 / 证据不足** | 表征缺失、互相矛盾、不能支持目标产物，或关键输入不足 |

**规则注意事项：**

- 不把“典型文献收率”直接作为普适成功线。优先使用用户设定目标；若无用户目标，只描述实测值和可比先例范围，不替用户定义成功。
- “未检出目标产物”只能在用户明确提供分析结果时使用；不能把空字段等同于实验失败。
- 文献数值只有在底物、规模、条件、分析/分离方式等可比性足够时才参与对照，并展示比较限制。
- 规则引擎输出触发字段和原因；LLM 不覆盖该判定。

### 8.3 建议排序

建议不是因果诊断，而是候选排查方向。可以按以下维度排序：与检索先例的相似度、证据质量、与当前条件的具体差异、建议是否能区分假设、风险/成本和用户约束。MVP 可以人工定义简明排序规则，不需要声称经过训练的预测模型。

## 九、团队分工

| 角色 | 主要负责 | 交付物 |
|---|---|---|

## 十一、演示方案

### 3–5 分钟演示顺序

1. **问题（20–30 秒）**：展示一条结构化实验结果，说明复盘需要对照实验记录和文献。
2. **输入（30–40 秒）**：录入反应类型、底物/目标产物、条件、收率和表征；指出用户目标是否提供。
3. **SciencePal 检索（45–60 秒）**：现场展示真实检索、来源和相关内容，说明它进入核心判断/排查流程的方式。
4. **结果评估（45–60 秒）**：展示规则状态、触发字段、用户目标与文献比较的边界。
5. **候选排查方向（45–60 秒）**：每条呈现证据、条件差异、反证/不确定性和可区分假设的验证方向。
6. **记录与局限（20–30 秒）**：保存本轮记录，说明适用范围和当前还不能自动判断的事项。

### 演示案例注意事项

原始构想中的 Suzuki 例子可作为占位案例，但“换 Pd 催化剂、提高载量、换溶剂、升温”等具体数值和引用必须先从真实来源核验。未经核验不得展示虚构的 ref A/B/C，也不要把文献中某一条件包装成对该底物的保证建议。

## 十二、风险与应对

| 风险 | 应对 |
|---|---|
| SciencePal 接入方式或权限与假设不符 | 10/16–18 优先做能力验证；如无 API，使用平台真实检索并如实记录人工步骤，不伪称自动接口 |
| 先例无法与用户实验直接比较 | 标出不匹配维度；降低证据等级；不据此硬做收率阈值或因果归因 |
| LLM 编造来源/过度归因 | 先检索再生成；引用字段只允许来自检索记录；逐条人工核验；无证据时返回证据不足 |
| 数据集太小 | 聚焦一个反应类别和少量高质量案例；把案例集定位为演示/验证样本，不宣称覆盖市场 |
| 用户输入缺失或表征含糊 | 追问关键字段，将状态设为未确认/证据不足，不用默认值补成事实 |
| 时间不够 | 先确保端到端主链路和提交材料，再考虑排序优化、历史展示和视觉润色 |
| 在线服务/评审链接不可用 | 提前测试公开访问权限；准备录屏、截图和本地备用演示；按赛事要求保证主链接有效 |
