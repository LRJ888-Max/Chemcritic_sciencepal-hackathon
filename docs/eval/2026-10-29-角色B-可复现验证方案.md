# 可复现验证方案：怎么保证「测得准」和「没改错」

2026-10-29 · 角色 B

问题来源：担心前面几轮测试判得不准，改的时候又怕把好的改坏。

这个担心是有实证的，不是心理作用。下面先给三个已实测的不确定源，再给对应的机械判定，最后给本次跑出来的真实基线和防改错的操作顺序。

---

## 一、三个「测不准」的源，都实测过

### 源 1：本地副本会落后于远端（本次实测发生过，现已同步）

2026-10-29 11:32 检查时，桌面副本落后于 GitHub main 一整轮：

| 文件 | 本地（11:32 旧版） | GitHub main | 差异 |
|---|---|---|---|
| `chemcritic_engine.py` | 72,944 B | 165,638 B | 远端大一倍多 |
| `records.json` | 14,571 B / 8 条 | 76,820 B / 32 条 | 底物 1 种 → 5 种 |
| `placement.py` | 8,489 B | 10,501 B | 远端有 `migration_targets`、`label_supported` |
| `--selftest` | 19 passed | 26 passed | 多 7 项 |

**后果不是「差一点」，而是结论相反。** 同一个用例 C5（口径被推定、但没给原话）：

| | 本地旧版 | 沙箱 |
|---|---|---|
| placement.status | `PLACED` | `UNDEFINED` |
| delta_vs_min | `-5` | `null` |

在旧版上测这一条会判「不合格」，然后让 C 去改一个他早就修好的地方。

**11:39 复查：目录已在凌晨同步（对应远端提交 `2026-10-28T16:13:13Z`）。146 个文件哈希全部相等，本地与沙箱跑同一套契约字段级 0 差异，C5 两边都是 `UNDEFINED`。**

所以这条风险的准确表述是「随时可能再次发生」，不是「一直存在」。`--fetch` 的价值就在于：你不必先判断当前处于哪种状态，直接测远端那份。**但如果目标是验证自己刚改的本地代码，就必须测本地，不能测远端。**

### 源 2：人工判分没有固定标准

同一个输出，我判「部分通过」，换个角度看可能是「通过」。前四轮里我改口过三次（record_id、8 条措辞、T4 是否致命），每次都是因为判据凭印象。

### 源 3：没有基线，改完不知道动了什么

`placement.py` 改两行，可能让 C1 的差值变了，也可能让 C4 的无参照判定退化了。没有改前改后的对比，这种退化只能等演示时才发现。

## 二、解法：把判定拆成两层，各用各的工具

判定层是确定性的，就不该用眼睛；措辞层是模型生成的，就用特征匹配。

### 层 1 · 引擎契约（`tests/engine_contract.py`）

把六条用例写成断言，跑一次出 pass/fail。

```bash
python tests/engine_contract.py --fetch
```

断言不是「当前行为」，是「规则推导出的正确行为」。每条在 `cases.json` 里有 `rule` 字段写依据。允许改断言，但必须同时改 rule——否则就成了「让测试通过」而不是「让行为正确」。

`ref_set` 用精确集合，不用「包含」。多一条和少一条都算错，**多出来的那条通常就是底物污染**。

### 层 2 · 措辞特征（`tests/wording_lint.py`）

把平台输出整段粘进 txt，跑一遍，得到命中清单。

```bash
python tests/wording_lint.py draft.txt --case R1
```

`--case` 声明用户到底给了哪些值。输出里出现用户没给的数字，直接报编造。11 条硬性规则覆盖了前四轮所有复发问题：替用户指定碱、补 1.2 当量、补 mol%、补「无水」、给区间、思维链泄漏、L1/L2 术语、记录编号、第一层吐第二层内容。

## 三、本次基线：3 个失败，同一个根因

```
C1 主场景      FAIL   ref [40, 50, 93, 99]，应为 [40, 50]
C2 残缺输入    pass
C3 库外底物    FAIL   delta = 0，应为 null
C4 跨口径      pass
C5 口径推定    pass
C6 4-溴甲苯    FAIL   ref 与 C1 完全相同
```

### 根因只有一处

`engine/placement.py`：

```python
124:  same_class = [r for r in records if r.outcome_type == user.outcome_type]
141:  same_tier  = [r for r in same_class if r.tier == tier and ...]   # 仍不看底物
```

只按收率口径和档位过滤，**不看底物对**。而同一个文件第 150 行的 `migration` 计算里用了 `_same_pair(user, r)`——说明这个函数是现成的、正确的，只是没用在参照池上。

### C1 和 C6 的池子完全一样，这是最硬的证据

| 用例 | 用户底物 | 引擎返回的参照池 |
|---|---|---|
| C1 | 4-溴苯甲醚 | `[40, 50, 93, 99]` |
| C6 | 4-溴甲苯 | `[40, 50, 93, 99]` |

两个不同底物拿到同一个池子。93 和 99 是 4-溴甲苯的两条档 A 记录（P30、P28），40 和 50 是 4-溴苯甲醚的（SM-001b、P36）。**双向污染。**

修好之后：C1 应为 `[40, 50]`，C6 应为 `[93, 99]`。**只让一边通过，等于没修。**

### C3 是同一个 bug 的另一面

3-溴噻吩在库里不存在，`verdicts` 全部 `BLOCKED`，但 `placement` 返回 `PLACED`、`delta = 0`——拿 4-溴苯甲醚的 40 跟用户的 40 相减。

前两轮线上测试里模型没有照抄这个 delta（它读了 verdicts 自己仲裁），所以没暴露。但这是靠模型兜底，不是靠设计兜底。

## 四、一个必须更新的结论：参照已经不是单点了

之前所有话术都建立在「档 A × 分离收率只有 1 条（40%）」上。**这个前提已经过期。**

`P36`（Weeden et al., Molecules 2011，即 CB-03）已经签核进库，50% isolated、档 A。所以修好底物过滤之后，C1 的真实参照是 **2 条：40 和 50**。

影响三处：

1. **区间可以给了。** 同档同口径两条构成区间 40–50%，不再是「单点不构成区间」。
2. **演示话术要改。** 从「全世界只有一条能跟你比，它 40%」改成「同体系同口径两条：40% 和 50%，你 35% 低于下限 5 个百分点」。
3. **差值仍然只对 min 算。** `delta_vs_min = -5`，说明 35 比最低的 40 低 5 个点。这个是站得住的。

这一条我昨天给的判断是错的（说参照只有 1 条），以本节为准。

## 五、工具自己的可信度怎么保证

一个会误报的检查器，比没有检查器更糟。所以两个工具都做了正反两面验证。

### lint 的验证

| 样本 | 结果 |
|---|---|
| 线上 R1 真实输出（已知有 5 类问题） | 命中 6 项，W1/W3/W4/W5/W11 全部抓到 |
| 手工构造的合规输出 | 0 违规，0 误报 |

中途还发现 lint 自己漏了一次：`如 K₂CO₃ 2 当量` 没被抓到，因为原文用的是下标字符 `₃`，正则里写的是普通 `3`。**所以 lint 也必须拿已知违规验一遍，否则它只是个安慰剂。**

### 断言的可信度

每条断言的依据来自规则，不来自当前输出。C1 的 `ref_set: [40, 50]` 是查了记录表推出来的：4-溴苯甲醚 + isolated + 档 A 的已核验记录只有 SM-001b 和 P36。不是「照抄引擎现在返回什么」。

## 六、防改错的操作顺序（给 C）

```bash
# 1. 改之前：存沙箱基线
python tests/engine_contract.py --fetch --snapshot /tmp/before.json

# 2. 改代码
#    placement.py:  same_class 与 same_tier 都加上 _same_pair(user, r)
#    顺带修:        soft_flags 里 "None vs n2" 渲染成「未记录 vs N₂」，且 kind=missing 不进差异列表

# 3. 改之后：存新快照并对比
python tests/engine_contract.py --fetch --snapshot /tmp/after.json --diff /tmp/before.json
```

### 通过标准（三条都要）

1. **C1、C3、C6 全部转 pass**
2. **C2、C4、C5 不许退化**——它们现在是 pass，改完必须还是 pass
3. `--diff` 输出里，**除 `ref_values` / `delta_vs_min` / `soft_details` 之外不许有意外变化**

第 3 条是防「改一个坏三个」的。如果 `C2.status` 从 `UNDEFINED` 变成了别的，就说明改动的影响面超出了预期，必须回头看。

### 一个容易白干的地方

改 `engine/placement.py` **不等于**改了沙箱。`bootstrap.sh` 从 GitHub 拉的是 `skills/chemcritic-comparability/scripts/chemcritic_engine.py`，必须跑 `engine/build_bundle.py` 再 push，否则 `--fetch` 拉到的还是旧包。

判断方法：改完先跑 `--fetch`，如果结果没变，八成是没打包。

## 七、这套东西不能保证什么

诚实说清边界，免得被它误导：

1. **只覆盖 4 个底物 × 2 种口径。** 通过只代表「已测过的行为没退化」，不代表全库正确。新加底物要加用例。
2. **lint 只能抓已知形态。** 它列出的是「我们见过它这么错」的清单。第 12 种编造方式出现时，lint 不会报警。
3. **模型层不可断言。** 同一输入理论上可能给两种说法。所以措辞层只能事后检查，不能事前保证。
4. **不覆盖追问多轮。** C2 只测「第一轮是否追问」，没测「用户答了之后是否收敛」。

这三条不需要现在补。但答辩时如果评委问「你们怎么保证不出错」，答案应该是「我们把判定层做成了可回归的 6 条契约 + 26 项自检，措辞层做成了 11 条特征检查」，而不是「我们测了很多次」。
