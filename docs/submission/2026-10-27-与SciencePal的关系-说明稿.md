## 5. 与 SciencePal 的关系：用在哪个环节

**一句话：我们把"判定"放进了 SciencePal 的沙箱，而不是放在提示词里。**

### 5.1 实际使用的三项能力

| 能力 | 具体用法 |
|---|---|
| **沙箱代码执行**（核心环节） | 判定引擎以单文件形式上传递沙箱，逐条读取记录、执行 8 项门槛、输出证书 JSON（含逐维结果、阻断维度、解锁条件、校准级别） |
| **智能体编排** | Agent Co-Building 配置系统提示词、绑定知识库、生成 Share Link 供评审访问 |
| **个人知识库** | 收录 11 篇开放获取文献全文 + 40 条带 locator 的 entry 级记录 + 门槛规则/口径词典/已知陷阱文档 |

### 5.2 明确没有做到的（如实披露）

- **对 PDF 知识库的自主检索尚未完成端到端验收**。运行记录中 `live_retrieval_performed = false`。
  当前流程是"结构化文献库 + 沙箱程序"：Agent 从结构化记录库取数并调用引擎判定，而不是对 PDF 做语义检索。
- **子 agent 并行机制推演未接入**。当前由单 Agent 依机制库顺序推演，并在输出中注明"本次未并行"。
- 序贯实验设计的自动化未接入，目前以决策树文本形式给出。

**说明：** 我们选择优先把"判定可审计"做实，而不是把"检索更花哨"做实。原因见 5.3。

### 5.3 为什么把判定放进沙箱——这不是实现细节，是产品红线

同一个案例，两种实现方式的结果对照：

| | 提示词内口算（实测） | 沙箱内执行引擎（实测） |
|---|---|---|
| **判定来源** | 模型推理 | `gates.py` 确定性计算 |
| **同一输入** | 输出会漂移 | 永远同一输出 |
| **实测表现** | 编造"Molecules 2012, Table 1 entry 10，NMR 86%"（该记录在库中不存在）；把口径未决的 35.0% 当成确定 GC 收率 | 8 条记录的 `verdict` 与本地引擎逐条一致（**8/8**） |
| **可审计性** | 无 | 每对参照输出一张证书：8 维逐项 PASS/FAIL/UNKNOWN、软维标注、阻断维度、解锁条件、校准级别、是否同篇非独立 |

**"判定退化为 LLM 口算"正是本产品要解决的病，也是它必须避免的死法。**
把判定移入沙箱、由确定性代码给出 `verdict`、模型只负责把证书翻译成用户语言——这是我们对这一点的工程回答，而不是架构偏好。

### 5.4 三条由平台实测驱动的修正

平台运行暴露的字段处理问题，逐条修掉：

| 现象 | 修正 |
|---|---|
| 口径未决（`unknown`）却被标为"已校准"（仅因原文有内标） | 口径未决时，校准级别保持 `unknown` |
| 把"醇类溶剂"的名称当作含水的证据 | 只描述溶剂记录差异，不据名称推断含水性 |
| 气氛未记录，被写成"与文献气氛不同" | 改为"气氛记录缺失，无法比较" |

三条同属一类错误：**把字段缺失当成了事实差异**。

这也解释了为什么判定里 `FAIL`（确定不可比）与 `UNKNOWN`（不知道）必须分开——它们对应两种完全不同的用户动作：前者"禁止同框"，后者"去补一条证据"。合并成一个"不确定"状态，是同类系统最常见的退化。

### 5.5 这一节的局限

1. 知识库检索链路未验收，因此本产品**不应被描述为"文献检索系统"**；它的定位是**文献数值的可比性判定系统**，输入是已核验的记录集合。
2. 记录集合规模为 40 条，其中"同底物 + 同口径 + 可校准"的最多 5 条（**可比性赤字 12.5%**）——这个比例本身就是我们测出来的结论之一。
3. `gold set` 与规则同源，指标（FPR/FNR/BDA/CAL）只证明规则一致性，不证明泛化能力。

## 附：一句话版（放摘要或封面用）

> ChemCritic 把"文献数值能不能放在一起比"做成确定性判定：判定在 SciencePal 沙箱内由代码执行、逐条输出可回查的证书，模型只负责解释，不得改写结论。

## 附：答辩口播版（30 秒）

> 我们没有让模型判断"你的收率正不正常"——那是它最擅长编、也最不该做的事。
> 我们把判定写成代码，放进 SciencePal 的沙箱里跑，每一对参考都出一张证书。
> 同一个案例，模型口算会给你一个编造的文献值；引擎跑出来会说"这条口径没写清，先别比"。
> 前者听起来更有用，后者才是能写进决策的东西。
