# 知识库框架（KB）

**状态：** 框架已搭好，**内容待 A 确认后入库**（清单见 [proposed-content.md](proposed-content.md)）
**建立日期：** 2026-10-25

---

## 1. 为什么 KB 是产品本体，不是附件

ChemCritic 的判定链条是：**检索 → 抽取 → 过闸 → 定位**。

其中"检索"这一步，如果只是让 LLM 凭记忆或凭网页搜索，会出现两个致命问题：

1. **引用不可追溯**——模型说的表号可能是编的
2. **同样的查询两次结果不同**——不可复现，Demo 会翻车

所以 KB 承担的是**证据源**的角色：每条数值必须能落到"哪个文件、哪一页、哪张表、哪一行"。这也是赛题"可运行、可展示、可复现"的具体落点。

> 一句话：**KB 不是为了"让模型知道更多"，是为了"让模型说的每个数字都有出处"。**

## 2. 四层结构

```text
KB/
├── L1 证据层（evidence）      原始 PDF —— 唯一的事实来源
├── L2 记录层（records）       entry 级结构化记录 —— 抽取产物，带 locator
├── L3 规则层（rules）         8 维门槛、分档定义 —— 判定依据
└── L4 辅助层（lexicon）       口径词典、已知陷阱 —— 提高抽取与判定的一致性
```

| 层 | 放什么 | 谁维护 | 检索时用来干什么 |
|---|---|---|---|
| **L1** | 开放获取论文 PDF | C 上传 | 回答"原文到底怎么写的" |
| **L2** | 每条数值一行：值/口径/条件/locator/证据等级 | A 核验后写入 | 回答"有哪些可比先例" |
| **L3** | 8 维门槛表、分档判据 | A 签字 | 回答"这条能不能比" |
| **L4** | 口径词表、踩过的坑 | A/B 补 | 回答"这个说法算哪个口径" |

**L1 与 L2 的关系：** L2 是 L1 的索引，不是替代。任何 L2 记录都必须能靠 `locator` 翻回 L1 的对应位置——翻不回去的，L2 记录作废。

**L3 进 KB 而不是只写在提示词里**，理由：规则会被检索到、会被引用，Agent 输出"卡在维度 4"时能指向 KB 里的规则原文，而不是"模型觉得"。

## 3. 命名与元数据规范

### 文件命名

```text
L1:  {source_id}_{第一作者}{年份}_{期刊缩写}.pdf
     例：SM-001_Miyaura1981_SynthCommun.pdf
L2/L3/L4: 英文小写短名 + .md，例：records.md / gates.md / outcome-lexicon.md
```

### 每条记录的必需字段（L2）

| 字段 | 说明 | 缺失后果 |
|---|---|---|
| `record_id` | 唯一标识，如 `SM-001-isolated` | 无法引用 |
| `source_id` | 所属文章，同文多 entry 共享 | 无法判断是否独立来源 |
| `value` / `outcome_type` | 数值 + 口径（isolated / gc / nmr / conversion / unknown） | 无法分堆 |
| `label_raw` | **原文措辞逐字** | 无法验证口径（维度 4 第一层直接 UNKNOWN） |
| `locator` | 表号 + entry + 脚注 + 页码 | 不可核验，记录作废 |
| `evidence_grade` | `A_confirmed` / `imported_unchecked` / `candidate` | 无法判断能否参与比较 |
| `conditions` | 催化剂/载量/碱/溶剂/温度/时间/气氛/规模/当量 | 软维度无法标注 |

完整 schema 见 [schema.json](schema.json)。

## 4. 检索策略（写进 Agent 提示词）

**三个固定查询模板：**

```text
① 底物检索："{芳基卤} + {硼酸} Suzuki 收率"        → 期望命中 L2 的 record
② 口径检索："{数值} 的收率类型 / assay / 内标"       → 期望命中 L2 的 label_raw
③ 规则检索："{某个维度} 的判定条件"                  → 期望命中 L3
```

**命中合格标准（三条同时满足）：**

1. 返回带 **表号或脚注**，不只是论文标题
2. 能对应到 L2 的某条 `record_id`
3. 对不上的命中必须进 `unmatched_hits`，**不静默丢弃**

> 第 3 条是产品诚实性的关键：**检索没命中，和检索命中但证据不支持，是两件事，必须分开显示。**

## 5. 更新流程（谁能加、加之前要什么）

```text
新增文献
  ↓
① C 上传 L1（PDF）→ 记录 DOI、许可、开放获取状态
  ↓
② extract.py 生成候选（outcome_type 一律 unknown）
  ↓
③ A 确认口径与 locator（每条 3 个问题，3–5 分钟）
  ↓
④ 写入 L2，标 evidence_grade
  ↓
⑤ 重跑 python engine/run_demo.py，确认测试不退化
```

**规则（L3）的更新更严格：** 任何改动必须同时更新 `docs/rules/` 与 `engine/gates.py`，并跑通 T1–T15。**改规则不跑测试，等于没改。**

## 6. 禁止入库的内容

| 内容 | 原因 |
|---|---|
| 付费墙后的 PDF | 许可风险；只放 DOI 与可打开的官方入口 |
| 未核验的候选池（34 条原始记录） | 会污染检索：Agent 会把"待核验"当成"已核验" |
| 用户自己的实验原始数据 | 与文献证据混淆；应单独存放并标注 `simulated` / `user_report` |
| 竞品宣传页、商业资料 | 与本产品判定无关 |
| 任何"推测出来的"字段值 | 违反"抽不到就留空"原则 |

## 7. 与代码的对应关系

| KB 层 | 对应代码 | 说明 |
|---|---|---|
| L1 | `engine/extract.py` 的输入 | PDF → 候选表格行 |
| L2 | `data/records.json` 的镜像 | KB 里放人可读的 `records.md`，代码读 JSON |
| L3 | `engine/gates.py` + `engine/tier.py` | KB 里放规则原文，代码里是实现 |
| L4 | `engine/gates.py::_LABEL_HINTS` | 词典以代码常量 + KB 文档双份存在 |

> **双份存在的理由：** 评审看 KB 里的规则原文，C 看代码里的实现；两者不一致就是 bug，测试会抓。
